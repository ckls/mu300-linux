# 系统补丁网页首次应用与加载状态修复（2026-10-26）

## 已确认的问题

1. 网页上传使用 `upload.ota`，第一次切入隔离更新环境时没有传递用户确认的检查 ID。CLI 只能从内容寻址的上传文件名推导 ID，因此返回 `Inspect this patch before applying`。第二次请求借用了此前准备好的运行环境，掩盖了第一次的交接错误。
2. 准备运行环境、冻结上传文件和再次检查补丁都在启动 RPC 内同步完成，可能超过网页请求时限。任务本身可以继续完成，页面却先弹出超时错误。
3. 上传、检查与确认后缺少连续的阶段提示；状态查询超时也没有区分“写入失败”和“暂时无法确认进度”。

## 修改

- 启动请求只执行任务准入、持有互斥锁并启动后台准备进程，立即返回任务 ID 和排队状态。后台进程冻结并校验用户审阅过的文件，准备隔离环境后直接进入执行器，锁跨进程与 exec 保持。
- 生成的补丁 bootstrap 显式传递检查 ID；网页后台也兼容旧补丁的只读 inspect 入口，避免重复调用 start 丢失 ID。
- 在隔离环境内准备下一次运行环境时，通过 PID 1 根目录访问真正的主机 tmpfs，避免普通根目录 bind 未包含 `/tmp` 子挂载造成路径不可见。
- 所有 OTA RPC 禁止请求合批，避免被其他慢调用一起拖住。
- 上传使用按钮动画和 LuCI 原生文件上传进度；检查、准备、写入、恢复、删除及重启显示主题适配的全局动画。确认弹框出现时移除遮罩，取消确认不执行写入。
- 超时后先核对同一任务的命令和补丁 ID。确认仍在执行或已经完成时展示真实状态；不会自动再次提交更新，也不会用其他历史任务的成功掩盖当前错误。
- 写入计数仅在事务 ID 与当前任务匹配时展示；中、英、土耳其语及浅色、深色和手机尺寸均覆盖。

## 验证

E5 与 MU300 两仓库分别运行：

- `python3 -m unittest discover -s installer/tests -p 'test_ota*.py'`：121 项通过。
- `node installer/tests/ota_luci.js`：异步页面流程、失败请求、连接丢失后确认、撤销、查询故障与恢复通过。
- `python installer/tests/ota_loading_browser.py`：18 个真实 Chromium 页面组合通过（3 种语言 × 2 种主题 × 3 个宽度），覆盖上传、检查、确认、准备、写入与完成。
- 首次更新集成测试实际执行 fork/exec、持锁和临时根目录文件更新，只确认一次即可完成；隔离挂载入口被测试替换，不是实机刷写测试。
- 另核对生成的 bootstrap 对通用 `upload.ota` 显式传递检查 ID，以及完成状态重建保留原任务身份。

本轮未重新提交用户已经完成的更新，未改写设备 NV，也未通过重启掩盖问题。以上为源码和离线回归结果；没有把这些改动描述为已部署的固件或已验证的实机 OTA。
