# 后台短信发送与未插卡看板检查（2026-10-28）

## 已确认并修复

- **发送失败的协议缺陷已复现**：发送器从 `25f8d0ce5` 起使用 `AT+SPACTCARD=0/1;+CMGS=…<CR>PDU<Ctrl-Z>` 原子选卡提交；`f0b5ad43` 引入的 ucode 守护进程却只允许裸 `AT+CMGS/CMGW` 携带 CR，因此后台网页发送和短信转发的合法提交在到达基带前被拒绝。现在校验器接受可选的单个 `SPACTCARD=[01];` 前缀，原样向原通道发送；其他命令拼接、非法卡号、LF、非十六进制或缺 Ctrl-Z 仍拒绝。FIFO 和 ubus 共用同一校验器。
- `mu300-at` 的 `exec 9<> "$DIR/cmd" 2>/dev/null` 会永久改变自身 stderr，导致后续 FIFO 超时、空应答和不完整应答的错误被吞掉。改为局部重定向，仅隐藏打开 FIFO 的系统错误；具体失败原因仍交还调用方。
- `mu300-sms send` 保留提交阶段的错误输出和退出状态。没有 `+CMGS` 且没有基带错误时，明确报告“没有提交确认、投递状态未知”，不再只有空白 `submit failed`。
- 未插卡过滤曾将整个 `ident` 清空，连设备 IMEI、厂商、模组型号和固件一起隐藏。现在仅清除卡身份和驻网数据，保留设备身份及真实射频状态；已同步 E5 公共页面。后端原有身份读取不依赖驻网成功，无须增加 AT 查询。

## 未证实的群友归因

尚未复现“继承后台环境、信号或描述符必然导致发送失败”。当前正常 FIFO 客户端使用单调时钟与原子应答文件轮询，不用 `read -t` 等待 FIFO 回复；`read -t` 出现在 shell 能力探测及无守护进程时的直连路径。

清空环境会移除 `MU300_SIM_SLOT`，使发送器不再添加选卡前缀，恰好绕开上述拒绝，但也失去了发送卡槽保证。这是对“干净环境恢复”的代码解释，不能当成对群友实际进程状态的采集证明。

没有加入 `env -i`、新会话包装或失败重发。前者可能丢失卡槽和事务锁环境；后者可能在 Ctrl-Z 已提交而确认丢失时重复发送。原有 SMSC 刷新、IMS、PDU 模式及 CMGS 顺序不变，收发通道所有权不变。

短信转发调用相同发送器，因此共享客户端修正；转发历史仍使用既有 `delivery_failed` 分类。E5 发送走 ModemManager/E5SMS，没有套用 MU300 FIFO 客户端改动。

## 换行正文的独立缺陷及修复

`utf8_to_ucs2` 原先按行 `print`，将正文的换行变成十六进制串里的真实 LF，随后被客户端的 FIFO 单行校验拒绝；仅含换行的正文还可能被错误编码为空内容。短信转发模板的来源行与正文之间本来就有 LF，因此单行原文也会踩中。

现在将每个原始 LF 编成 `000A`、CR 编成 `000D`，十六进制串始终只有一行；保留首尾空行、CRLF、中文及代理对。增加一个输入记录终止符，让 POSIX/BusyBox awk 都能精确保留尾部 LF，不依赖 BusyBox 不一致的 NUL 记录分隔行为。CMGS 长度及 UDL 从正确编码后的字节计算。

同时修复转发从池文件读正文时命令替换吞掉尾部空行的问题，仅移除存储格式附加的一个终止 LF。两仓库的转发长度检查均计入全部 LF；E5 发送器读取文本文件时保留 CRLF，不经 Python 通用换行转换。

回归：发送事务 14 项、转发模板/长度 4 项、转发历史/正文读取 6 项通过；原生 ucode 双卡完整模拟链路 4 项通过，包含多行中文、CRLF 及尾部空行的 UTF-16 字节校验。原生 jshn/ucode 的隔离转发夹具验证 JSON、模板 JSON、纯文本、钉钉、SMTP Base64 和短信转发正文，所有传输端均被替换，无实际外发。E5 长度检查及双卡发送共 5 项通过。
